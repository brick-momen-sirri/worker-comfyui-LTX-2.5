# LTX 2.5 UHD generation and upscaling

These ComfyUI compositions are not the full official DFR pipeline. For that implementation, see [the DFR worker](dfr-4k.md).

Two additional modes target **3840×2160** video using the existing INT8 model bundle. **Image-to-video completed real nine-frame and 33-frame 4K jobs on a user-confirmed 48 GB Runpod GPU**, with successful S3 delivery and browser media loading. Start with the default **nine frames at 24 fps** preset; the frame-count limit remains **33**. The exact GPU model and peak VRAM were not measured, and the separate video-upscale mode still needs qualification. The original 18 modes retain their existing limits.

| Mode | Required input | Processing dimensions | Output |
|---|---|---|---|
| `image_to_video_4k` | `media.image` | 960×544 image-to-video → 1920×1088 latent refinement → 3840×2176 pixel IC-LoRA upscaling | Center crop to 3840×2160 |
| `video_upscale_4k` | `media.video` | Normalize source to 1920×1088 → 3840×2176 pixel IC-LoRA upscaling | Center crop to 3840×2160 |

The final crop removes eight rows from the top and eight from the bottom. Generation stays on the model's aligned spatial grid before that crop. `width` and `height` describe the first column of processing dimensions, and are fixed for each mode; supplying 3840×2160 as the input dimensions is rejected.

These graphs compose the pinned [official two-stage image-to-video workflow](https://github.com/Lightricks/ComfyUI-LTXVideo/blob/15d09abb5a187a8dcaea2fc31fe51ee96e6c9d0d/example_workflows/2.5/LTX-2.5_T2V_I2V_Two_Stage_Distilled.json) and [IC-LoRA video-to-video workflow](https://github.com/Lightricks/ComfyUI-LTXVideo/blob/15d09abb5a187a8dcaea2fc31fe51ee96e6c9d0d/example_workflows/2.5/LTX-2.5_V2V_ICLoRA_Single_Stage_Distilled.json). The UHD composition and final crop are this worker's adaptations. The [official Pixel Spatial Upscaler model card](https://huggingface.co/Lightricks/LTX-2.5-22b-IC-LoRA-Pixel-Spatial-Upscaler) specifies a **2×** model, reference downscale factor **2**, and LoRA strength **1.0**. Image-to-video obtains its overall 4× size through two successive 2× stages; it does not load a 4× LoRA.

The upscaler generates fine detail and can change it. Use a clean source clip whose framing matches the desired result. It is a creative generation stage, and does not guarantee exact restoration of the original detail. [Official intended use and source requirements](https://huggingface.co/Lightricks/LTX-2.5-22b-IC-LoRA-Pixel-Spatial-Upscaler)

## Inputs and settings

Ready-to-edit requests are [image_to_video_4k.json](../examples/image_to_video_4k.json) and [video_upscale_4k.json](../examples/video_upscale_4k.json). Replace the example HTTPS URL with a readable S3/R2 object URL or presigned GET URL. Each accepts a base64 object or data URI instead:

```json
"media": {"image": "data:image/png;base64,REPLACE_WITH_BASE64_IMAGE"}
```

```json
"media": {"video": {"base64": "REPLACE_WITH_BASE64_MP4"}}
```

Use URLs for video and large images to stay within Runpod request limits. The [local tester](runpod-tester.md) can upload a selected file to S3/R2 and fill its URL automatically. Source-upload credentials stay in the local tester; generated-result S3 credentials remain separate Runpod worker environment variables.

Both modes default to nine frames, accept **9, 17, 25, or 33 frames**, and default to **24 fps**. Nine frames produce approximately 0.375 seconds; 33 produce approximately 1.375 seconds at 24 fps. The manifest accepts integer FPS values from 1 to 60, but qualification starts at 24. Raising FPS does not interpolate extra frames. The frame-count limit is an admission policy, not a guarantee that 33 frames fit in VRAM.

The prompt and seed are configurable. Image-to-video also accepts `image_strength` from 0 to 1 and `image_compression` from 0 to 100. CFG, pixel LoRA strength, and control strength are fixed to **1.0**. Sampling follows the shipped distilled schedules; arbitrary `steps` or `denoise` values are unsupported. The full contract and API graphs are in [the workflow manifest](../workflows/manifest.json), [image_to_video_4k.json](../workflows/image_to_video_4k.json), and [video_upscale_4k.json](../workflows/video_upscale_4k.json).

The updated worker's named API validates and normalizes source video, resamples it to the selected FPS, trims it to the requested frame count, and resizes/center-crops it to 1920×1088. Short videos are rejected. Existing source audio is normalized and retained as conditioning/output; silent input receives a silent track. The final result follows the existing Runpod job ID, ComfyUI `prompt_id`, `videos` response array, and required S3 upload behavior. Completion is reported only after those required uploads succeed. See [the API contract](API.md) for response and error examples.

## Use the existing endpoint through the local tester

The tester's default 4K transport compiles the selected **shipped** graph into the existing `workflow` plus `images`/`videos` request format. This lets the deployed INT8 image execute the new graph using its already bundled models and nodes. The existing worker must allow that API with `ALLOW_CUSTOM_WORKFLOWS=true`. Restart the updated local tester and reload the page, select one of the 4K modes, retain nine frames and 24 fps, supply the source, and click Run.

This compatibility transport bypasses the updated worker's named-media normalization. For `video_upscale_4k`, supply a **24 fps source with an audio track**, containing at least the requested number of frames. The graph normalizes framing to 1920×1088, but this path does not provide the native worker's FPS conversion or silent-audio insertion. Use the native transport after updating the deployed image when those features are needed.

The JSON examples above are **named-mode** requests for the updated worker. Sending them directly to the old image will fail because that image does not know the new mode names. The tester performs the compatibility translation for you. It does not automatically retry a submission whose acceptance is uncertain; check the existing job before submitting again.

## Build and deploy the updated named API

The extension reuses the completed INT8 image and its eleven models. It requires **no additional model downloads or dependencies**. **Build status on 2026-09-12:** the new image has not been built or pushed because the local Docker Desktop Linux engine is unavailable. The successful 4K job used the already deployed image plus the trusted graph through the tester, so this build is not required for that working compatibility path. Once Docker is available, build the additional application layer from the workspace:

```powershell
cd D:\worker-comfyui-LTX-2.5
docker build --platform linux/amd64 -f Dockerfile.4k --build-arg BASE_IMAGE=worker-comfyui-ltx25:int8 -t momensirribrick/worker-comfyui-ltx25:int8-4k .
```

`BASE_IMAGE` must identify the full INT8 image already built locally, or an accessible equivalent registry image. For repeatable deployment, use its immutable digest. The thin build reuses model layers; it still produces a complete image with the same model storage requirement. Keep the [existing deployment disk/RAM allowance](build-research.md).

After qualifying the image, publish the separate tag:

```powershell
docker push momensirribrick/worker-comfyui-ltx25:int8-4k
```

Select that image on the Runpod worker template, keep the endpoint's existing result-delivery environment variables and secrets, and retain the previous image tag for rollback. Use an **RTX 6000 Ada 48 GB** worker with **64 GB or more system RAM** as the starting qualification environment. The original RTX 6000 24 GB is a different GPU; neither it nor the local 24 GB card has been qualified for these 4K graphs.

After deploying the new image, start the tester in named mode:

```powershell
$env:RUNPOD_TESTER_4K_TRANSPORT = "named"
python tools/runpod_tester/server.py --endpoint dfadob3rm5dg32 --open
```

In WSL, use `RUNPOD_TESTER_4K_TRANSPORT=named python3 tools/runpod_tester/server.py --endpoint dfadob3rm5dg32` from `/mnt/d/worker-comfyui-LTX-2.5`, then open [localhost:8766](http://localhost:8766). Omit that environment setting to use the default compatibility transport.

The new worker uses separate 4K admission limits selected by trusted manifest metadata:

| Environment variable | Default | What it limits |
|---|---|---|
| `MAX_4K_GENERATION_PIXELS` | `2088960` | Requested source dimensions, up to 1920×1088 |
| `MAX_4K_OUTPUT_PIXELS` | `8355840` | Aligned render before cropping, 3840×2176 |

Do not set the output limit to 3840×2160: the larger aligned render must fit first. Existing `MAX_GENERATION_PIXELS` and `MAX_OUTPUT_PIXELS` still govern the original modes. `MAX_GENERATION_FRAMES` and duration policy can impose stricter limits. Callers cannot select the 4K admission policy by adding a request field. These checks control admitted jobs and do not reserve or measure GPU memory.
